# Carbon Signal: двухрежимный редизайн «Старосты»

Дата: 2026-09-15

Статус: дизайн согласован, реализация не начата

## Цель

Сделать интерфейс визуально презентабельным и узнаваемым, сохранив скорость рабочего журнала. Приложение должно иметь две версии в одной оболочке:

1. Общая версия для группы, доступная без пароля.
2. Полная версия старосты, бесшовно включающаяся после проверки существующего ключа.

Текущий этап ограничен frontend. Backend, формат облачного состояния и API не изменяются.

## Зафиксированные решения

- Арт-дирекция: **Carbon Signal Balanced**.
- Архитектура интерфейса: один адаптивный frontend, а не две отдельные страницы.
- Общая версия доступна по умолчанию без авторизации.
- Общая версия показывает публичное расписание и учебную информацию.
- Режим старосты включается после ввода существующего ключа доступа.
- После успешного входа страница не перезагружается.
- Публичные дедлайны и личный кабинет студента отложены, поскольку требуют backend-изменений.
- В текущем этапе не добавляется хранение индивидуальных кодов студентов.

## Пользовательские режимы

### Общая версия

Общая версия предназначена для всей группы и не должна раскрывать данные защищённого журнала.

Доступные данные и экраны:

- расписание на сегодня;
- переключение даты;
- расписание БГТУ;
- текущая чётность недели;
- семестр и публичная учебная информация;
- справочная информация, которая уже доступна без ключа;
- форма входа старосты.

Недоступные данные и действия:

- ФИО и контакты студентов;
- индивидуальная и общая посещаемость из журнала;
- сдачи и дедлайны из защищённого состояния;
- платежи и сборы;
- создание, изменение и удаление данных;
- экспорт и резервные копии журнала.

Навигация общей версии должна содержать только реально доступные разделы. Предлагаемый набор: `Сегодня / Расписание / Семестр / Ещё`. Не показывать закрытые вкладки в disabled-состоянии.

### Режим старосты

После успешной проверки ключа frontend загружает защищённое состояние и раскрывает полный рабочий интерфейс.

Доступные разделы:

- Сегодня;
- Сдачи;
- Деньги;
- Группа;
- Ещё.

Режим старосты добавляет:

- посещаемость и быстрые отметки;
- рабочую статистику;
- создание и редактирование занятий;
- работы и дедлайны;
- сборы и платежи;
- список студентов и контакты;
- импорт, экспорт, резервные копии и настройки.

Роль обозначается компактным статусом «Староста» в интерфейсе. Не создавать отдельную тяжёлую административную панель.

## Авторизация и переход между режимами

Использовать существующие функции и API из `cloud.js`. Backend-контракт не менять.

Последовательность входа:

1. Пользователь остаётся на текущем публичном экране и открывает компактную форму «Войти как староста».
2. После отправки ключа интерфейс показывает состояние проверки внутри формы или рядом с действием входа.
3. Frontend вызывает существующую операцию проверки сессии.
4. При успехе загружается облачное состояние журнала.
5. Роль меняется с reader на editor.
6. Текущий экран обновляется на месте; появляются закрытые разделы, данные и действия.
7. Фокус переводится на подтверждение успешного входа или заголовок обновлённого экрана.

Не выполнять полную перезагрузку страницы и не отправлять пользователя на отдельный URL.

При неверном ключе:

- не очищать публичный экран;
- не менять навигацию;
- показать понятную локальную ошибку у поля;
- сохранить возможность повторного ввода.

При конфликте облачной ревизии:

- сохранить загруженный режим старосты;
- временно заблокировать редактирование;
- явно показать статус read-only и действия восстановления;
- не возвращать пользователя в общую версию.

При выходе:

- применить существующую очистку приватных данных и локальной копии;
- закрыть защищённые экраны;
- вернуть общую навигацию и публичное расписание;
- не оставлять персональные данные в DOM.

Сохранение ключа старосты между перезапусками приложения не добавляется в этом этапе. Текущая модель хранит ключ только в памяти вкладки; менять это без отдельного решения по безопасности не следует.

## Визуальное направление

### Характер

Интерфейс должен ощущаться как аккуратный цифровой инструмент с премиальной hardware-эстетикой: графит, тёплый оранжевый сигнал, мягкий направленный свет и строгая информационная сетка.

Он не должен выглядеть как стандартный бело-синий SaaS, неоновая игровая панель или набор одинаковых карточек.

### Композиция

- Крупные карточки используются для самостоятельных смысловых блоков.
- Однотипные элементы внутри блока объединяются в один контейнер.
- Строки расписания, списки студентов и похожие повторяющиеся элементы разделяются тонкими линиями.
- Не оборачивать каждую строку в отдельную скруглённую капсулу.
- Воздух, типографика и линии должны создавать основную иерархию.
- Скруглённая нижняя навигация остаётся самостоятельной плавающей поверхностью.

Пример для расписания: один контейнер с умеренным радиусом, внутри которого занятия разделены горизонтальными линиями. Статусы располагаются справа компактными метками.

### Карточки и скругления

Скругления не убираются полностью.

Использовать их для:

- главной сводки дня;
- объединённого блока расписания;
- диалогов и форм;
- нижней навигации;
- отдельных независимых сущностей;
- коротких статусных меток.

Не использовать их для:

- каждой строки одного списка;
- декоративных контейнеров без собственной функции;
- вложенных карточек с одинаковым радиусом;
- нескольких уровней капсул внутри одной карточки.

### Цвет

Тёмная тема:

- фон: почти чёрный тёплый графит;
- поверхности: графит с небольшим тёплым оттенком;
- основной текст: тёплый светлый;
- вторичный текст: приглушённый серо-бежевый;
- акцент: сигнальный оранжевый;
- границы: тёплый тёмно-серый;
- ошибки, успех и предупреждение сохраняют семантические различия и достаточный контраст.

Светлая тема:

- фон: тёплый бумажный;
- поверхности: светлый нейтральный;
- основной текст: графитовый;
- акцент: глубокий оранжевый;
- избегать чистого белого фона с обычным синим акцентом.

Оранжевый применяется для текущего состояния, основной CTA, статуса роли и важных сигналов. Не окрашивать им все кнопки и декоративные элементы.

### Типографика

- Заголовки могут использовать выразительную антикву или характерный display-шрифт.
- Рабочий текст, формы и списки используют хорошо читаемый гротеск.
- Крупные заголовки получают заметный контраст масштаба и плотный трекинг.
- Технические подписи, время и статусы могут использовать uppercase и увеличенный межбуквенный интервал.
- Основной текст не должен быть мельче 16 px там, где он читается как содержимое, а не служебная метка.
- Если подключение внешних шрифтов конфликтует с CSP или offline-режимом, шрифты должны поставляться локально либо использоваться надёжные системные замены.

### Движение

- После входа использовать короткое последовательное раскрытие закрытых элементов, 180–320 мс.
- Навигация должна перестраиваться без скачка высоты и положения.
- Новые блоки могут появляться через opacity и небольшой translateY.
- Не использовать постоянное свечение, параллакс и декоративное движение.
- Полностью учитывать `prefers-reduced-motion`.

## Главный экран

### Общая версия

Иерархия экрана:

1. Контекст группы и актуальность данных.
2. Выразительный заголовок дня.
3. Дата и чётность недели.
4. Одна акцентная карточка со сводкой расписания.
5. Один объединённый блок занятий с разделителями.
6. Ненавязчивое действие «Войти как староста».
7. Нижняя публичная навигация.

В публичном режиме не показывать фиктивные значения пропусков, долгов и сборов.

### Режим старосты

После входа экран сохраняет ту же композицию, но:

- приветствие может стать персональным;
- появляется статус роли;
- сводка получает рабочие показатели;
- строки занятий становятся действиями для открытия посещаемости;
- появляется контекстное действие добавления пары;
- нижняя навигация расширяется до полного набора разделов.

Не размещать на главной все административные кнопки одновременно. Редактирование и удаление должны находиться в контексте сущности или в её детальном экране.

## Компоненты

### App shell

Отвечает за:

- текущую роль;
- состав навигации;
- безопасные зоны PWA;
- основную ширину контента;
- переход между reader и editor.

### Header

Показывает контекст группы, дату, актуальность данных и роль. Не оформляется отдельной белой карточкой на каждом экране.

### Summary card

Одна акцентная поверхность с наиболее важной информацией текущего экрана. На главной общей версии содержит только публичные данные.

### Grouped list

Один контейнер для однотипных строк. Строки разделены линиями. Контейнер имеет единый фон, границу и радиус.

### Status label

Компактная прямоугольная метка с небольшим радиусом. Цвет кодирует состояние, но текст остаётся обязательным.

### Role-aware navigation

Получает список вкладок из текущей роли. При смене роли сохраняет стабильное положение и корректно выбирает доступный активный раздел.

### Login dialog

Открывается поверх публичной версии. Содержит видимый label, поле пароля, основное действие, отмену, состояние проверки и inline-ошибку.

## Состояния и ошибки

Для каждого основного экрана предусмотреть:

- загрузку;
- актуальные данные;
- пустой результат;
- сохранённые устаревшие данные;
- сетевую ошибку;
- отсутствие доступа;
- конфликт редактирования для старосты.

Ошибка загрузки защищённого журнала после корректной проверки не должна уничтожать публичное расписание. Пользователь получает возможность повторить загрузку или выйти.

## Адаптивность

- Основной приоритет: 375–430 px.
- Проверить 320 px без горизонтального скролла.
- На планшете и desktop не растягивать мобильную колонку бесконечно.
- На широком экране допускается двухколоночная композиция сводки и основного списка, если порядок DOM остаётся логичным.
- Touch targets не меньше 44×44 px.
- Нижняя навигация учитывает safe-area inset.

## Доступность

- Контраст обычного текста не ниже 4.5:1.
- Все действия доступны с клавиатуры.
- Focus-visible не скрывается тенями и overflow контейнеров.
- Иконки-кнопки имеют доступные названия.
- Текущая вкладка отмечается `aria-current="page"`.
- Статусы не передаются только цветом.
- Ошибки формы связаны с полем через `aria-describedby` и `aria-invalid`.
- После изменения роли объявляется краткий live-region статус.
- Анимация не является условием понимания перехода.

## Техническая стратегия

Рекомендуемый подход: единый адаптивный интерфейс.

- Не создавать отдельный HTML-документ для режима старосты.
- Сохранить текущую модель `render()` и существующие view-функции, меняя их постепенно.
- Ввести явное представление текущей роли на основе существующих `cloudHasSession()` и `cloudCanEdit()`.
- Разделять доступность данных и возможность редактирования: конфликт может оставить сессию активной, но сделать её read-only.
- Строить навигацию из декларативного списка доступных вкладок для роли вместо постоянного набора, скрываемого только CSS.
- Не полагаться только на CSS для защиты действий; существующая JS-проверка разрешений остаётся обязательной.
- Не встраивать read-only или editor-ключи в статические frontend-файлы.

## Файлы предполагаемой реализации

Это ориентир для следующей модели, а не требование переписывать всё сразу.

- `styles.css`: токены Carbon Signal, типографика, app shell, summary card, grouped list, role transition, темы.
- `index.html`: минимальная оболочка, мета-цвета темы и контейнер навигации.
- `app.js`: role-aware представления, главная общей версии, сгруппированные списки, состав разделов.
- `cloud.js`: встроенная форма входа/диалог, переключение режима после существующей проверки, статусы и выход.
- `dialogs.js`: визуальная интеграция формы входа, если будет использована общая диалоговая система.
- `tests/`: проверки публичного DOM, закрытых данных, перехода ролей и статических ассетов.

## Вне текущего этапа

- изменения backend и базы данных;
- публичный read-only endpoint дедлайнов;
- индивидуальные коды студентов;
- личный кабинет студента;
- сохранение студенческой сессии;
- создание и сброс кодов старостой;
- push-уведомления;
- новые сущности в облачном состоянии.

Отложенные задачи записаны в корневом `TODO.md`.

## Проверка результата

Автоматические проверки:

- общая версия не содержит персональных данных защищённого журнала;
- без сессии отсутствуют editor-действия и закрытые вкладки;
- успешная сессия раскрывает полный интерфейс без reload;
- неверный ключ не меняет текущий публичный экран;
- выход удаляет приватные данные из DOM и локальной копии;
- конфликт блокирует запись, но сохраняет режим просмотра старосты;
- существующие тесты облачной синхронизации и приватности проходят.

Визуальные проверки:

- 320, 375, 430, 768 и 1440 px;
- светлая и тёмная темы;
- общая версия и режим старосты;
- загрузка, пустое состояние, ошибка и конфликт;
- отсутствие россыпи отдельных карточек для строк списков;
- одна отчётливая визуальная иерархия без перегрузки оранжевым;
- переход после входа без скачка нижней навигации;
- клавиатурная навигация и reduced motion.

## Критерии приёмки

- Общая версия полезна без пароля и не раскрывает приватные данные.
- После существующего ключа полный журнал появляется без перезагрузки страницы.
- Визуально обе версии являются одним продуктом.
- Carbon Signal узнаваем по графитовой основе, тёплому оранжевому акценту и выразительной типографике.
- Крупные смысловые блоки используют карточки, а повторяющиеся строки внутри них разделены линиями.
- Backend и формат данных не изменены.
- Публичные дедлайны и личный режим студента не реализованы в этом этапе.
